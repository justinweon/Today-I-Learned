# 2026-10-28 TIL — FastAPI 입력 검증과 예외 처리

> 
식료품 재고 관리 API를 예로 들어, 요청에서 값을 받는 방법부터 입력 검증, 목록 필터링, 오류 응답까지 학습했습니다. 핵심은 **값을 받는 것, 검사하는 것, 저장하는 것, 응답하는 것은 서로 다른 단계**라는 점입니다.

## 2. 경로 변수와 쿼리 변수

경로 변수는 주로 특정 대상을 식별하고, 쿼리 변수는 검색 조건이나 조회 범위를 전달합니다.

| 구분 | 예시 | 의미 |
|---|---|---|
| 경로 변수 | `/groceries/8` | 8번 식료품 지정 |
| 쿼리 변수 | `/groceries?category=과일` | 과일 카테고리 조건 전달 |
| 여러 쿼리 | `/groceries?category=과일&limit=10` | 조건을 `&`로 연결 |

```python
# FastAPI 앱에 등록하는 경로 함수 예시
@app.get("/groceries/{item_id}")
async def get_grocery(item_id: int):
    return {"선택한_번호": item_id}
```

`/groceries/8` 요청이 오면 FastAPI가 경로의 값을 꺼내 정수로 변환하고 함수의 `item_id`에 전달합니다. 이 코드는 번호를 반환할 뿐, 실제 상품을 찾는 코드는 아닙니다.

쿼리도 마찬가지입니다. `category=과일`을 전달했다고 자동으로 검색되지는 않습니다. 서버에서 조건에 맞는 데이터를 고르는 코드를 작성해야 합니다. 이 수업의 GET 필터링은 저장된 상품의 카테고리를 변경하는 요청이 아닙니다.

경로 변수는 해당 경로에서 필수입니다. `/groceries`를 요청하면 `/groceries/{item_id}`에서 값을 생략한 것이 아니라 다른 경로를 요청한 것입니다. 목록 경로가 별도로 등록되어 있다면 그 함수가 실행될 수 있습니다. 특정 대상을 쿼리로 식별하는 방식이 HTTP 규칙 위반인 것은 아니며, 경로 방식은 여기서 채택한 설계 관례입니다.

## 3. 필수 입력, 기본값, None

쿼리 변수는 항상 선택 입력인 것이 아닙니다. 기본값을 어떻게 선언했는지가 중요합니다.

| 매개변수 선언 | 생략했을 때 |
|---|---|
| `category: str` | 필수 입력이므로 검증 오류 |
| `category: str = "과일"` | `"과일"` 사용 |
| `category: str \| None = None` | `None` 사용 |

`str | None`은 허용 타입을 나타내고, `= None`은 생략했을 때 사용할 값을 정합니다. `Optional[str]`도 `str | None`과 같은 타입 의미이며, 그 자체가 기본값을 지정하지는 않습니다.

`None`, 문자열 `"None"`, 빈 문자열 `""`은 서로 다릅니다. 또한 변수에 값이 들어온다고 화면에 자동으로 출력되는 것은 아닙니다.

```python
# 라우트 함수의 매개변수 선언에 사용하는 설정
q: str | None = Query(default=None, min_length=2, max_length=10)
```

이 설정에서 검색어 생략은 허용되지만, `?q=`는 빈 문자열을 전달한 것이므로 최소 길이 조건에 걸립니다. `?q=감`도 거절되고, `?q=사과`는 길이 조건을 만족합니다. `None`일 때 전체 목록을 보여주는 동작은 별도의 필터링 코드로 결정합니다.

## 4. Path와 Query의 검증 설정

`Path`와 `Query`는 입력 위치, 검증 규칙, 문서 설명 등을 FastAPI에 전달하는 도구입니다. 일반 파이썬 타입 힌트만으로 런타임 검사가 자동 수행되는 것은 아니며, 여기서는 FastAPI와 Pydantic이 검사합니다.

| 옵션 | 역할 |
|---|---|
| `gt` | 기준값 초과 |
| `ge` | 기준값 이상, 경계 포함 |
| `lt` | 기준값 미만 |
| `le` | 기준값 이하, 경계 포함 |
| `min_length` / `max_length` | 문자열 최소·최대 길이 |
| `pattern` | 정규표현식에 따른 형식 검사 |
| `description` | API 문서에 설명 표시, 검증 규칙은 아님 |
| `alias` | 외부 요청에서 사용할 이름 지정 |

```python
item_id: int = Path(gt=0)
limit: int = Query(default=10, ge=1, le=50)
code: str = Query(pattern="^[A-Z]+$", description="영문 대문자로 된 상품 코드")
q: str | None = Query(default=None, alias="query", min_length=1)
```

`limit`은 생략하면 10을 사용하고, 전달된 값은 1 이상 50 이하의 정수여야 합니다. `pattern="^[A-Z]+$"`는 영문 대문자가 하나 이상인 형식을 검사하므로 `APPLE`은 허용하고 `apple`은 거절합니다. 설명 문구만 바꿔도 검사 규칙은 바뀌지 않습니다.

`alias="query"`에서는 **외부 이름은 `query`, 내부 변수 이름은 `q`**입니다. `/groceries?query=우유`의 값은 함수 안에서 `q`로 사용합니다. 별칭은 값을 바꾸는 기능이 아닙니다.

요청 값이 선언한 조건을 만족하지 못하면 기본 설정의 FastAPI는 해당 경로 함수 본문을 실행하지 않고 422 응답을 보냅니다.

## 5. Annotated를 왜 사용하는가?

처음에는 기존 방식으로도 검증이 되는데 왜 `Annotated`를 사용하는지 헷갈렸습니다. 핵심은 **검증 능력을 추가하는 것이 아니라, 타입의 추가 정보와 기본값을 분리하는 것**입니다.

```text
매개변수 이름: 타입 설명 = 기본값
```

```python
# 기존 방식: Path 객체가 파이썬 문법상 기본값 자리에 있음
item_id: int = Path(gt=0)

# Annotated 방식: 검증 설정이 타입 설명 안에 있음
item_id: Annotated[int, Path(gt=0)]

# 타입, 검증 설정, 실제 기본값을 구분
q: Annotated[str | None, Query(min_length=2)] = None
```

`Annotated[타입, 추가 정보]`에서 `Annotated`는 정보를 묶는 틀이고, `Path(gt=0)`은 입력 위치와 조건을 담는 설정입니다. FastAPI가 그 설정을 읽어 검사합니다.

일반적인 위치 또는 키워드 매개변수에서는 기본값 있는 매개변수 뒤에 기본값 없는 매개변수를 선언할 수 없습니다. 예를 들어 `async def search(item_id: int = Path(gt=0), q: str):`는 함수 정의 단계에서 문법 오류가 납니다.

```python
from typing import Annotated
from fastapi import Path

# 함수 선언 방식 비교용 예시
async def search(item_id: Annotated[int, Path(gt=0)], q: str):
    return {"item_id": item_id, "q": q}
```

이 방식은 둘 다 기본값 없는 매개변수이므로 같은 순서로 선언할 수 있습니다. `Path(gt=0)` 안의 `=`는 함수 호출의 키워드 인자이지, `item_id`의 기본값 지정이 아닙니다.

기존 방식 자체가 잘못된 문법인 것은 아닙니다. 매개변수 순서를 맞추면 기존 방식으로도 검증할 수 있습니다. 또한 `Annotated`를 사용하더라도 `= None` 같은 기본값을 붙이면 파이썬의 매개변수 순서 규칙은 여전히 적용됩니다.

## 6. 필터링과 페이지네이션

필터링은 조건에 맞는 항목으로 새 결과 목록을 만드는 작업입니다. 조회 결과에서 제외하는 것과 원본 장부에서 삭제하는 것은 다릅니다.

```python
# 교안의 목록 조회 함수에서 사용하는 처리 흐름
results = list(grocery_database.values())
if category:
    results = [item for item in results if item["category"] == category]
if q:
    results = [item for item in results if q.lower() in item["name"].lower()]
page = results[offset : offset + limit]
```

카테고리는 같은 값인지 비교하고, 검색어는 이름에 포함되어 있는지 확인합니다. 필터링을 마친 다음 필요한 구간을 선택합니다. `list(...)`는 별도 목록을 만들지만 내부 상품 객체까지 깊게 복사하는 것은 아닙니다.

- `offset`: 앞에서 건너뛸 개수이자 이 슬라이싱의 시작 인덱스
- `limit`: 시작 위치부터 보여줄 최대 개수
- 슬라이싱: 시작 위치는 포함하고 끝 위치는 포함하지 않음

학습 중 `offset=0`을 “0번 항목을 빼기”로 혼동했습니다. 정확히는 아무것도 건너뛰지 않고 첫 항목부터 시작한다는 뜻입니다.

| 목록: 사과 → 우유 → 배 → 당근 | 결과 |
|---|---|
| `offset=0`, `limit=2` | 사과, 우유 |
| `offset=1`, `limit=2` | 우유, 배 |
| `offset=2`, `limit=1` | 배 |

`limit`은 최대 개수이므로 남은 데이터가 적으면 그보다 적게 반환합니다. 교안은 전체 메모리 목록을 먼저 필터링하므로, 반환 개수 제한이 전체 검색 작업량까지 없애주는 것은 아닙니다.

## 7. Pydantic 입력 모델과 검증 순서

상품 등록처럼 여러 정보를 보낼 때는 요청 본문에 JSON 데이터를 담습니다. `GroceryCreate`는 그 데이터의 구조와 검증 규칙을 정의하는 입력 모델입니다.

교안의 주요 규칙은 이름 길이 2~50자, 가격은 0 초과, 수량은 0 이상, 유통기한은 날짜 타입입니다. `Field(..., gt=0)`의 `...`은 필수 입력이라는 뜻입니다.

다음은 교안의 검증 핵심을 정리한 모델 예시입니다.

```python
from datetime import date
from typing import Self
from pydantic import BaseModel, Field, field_validator, model_validator

class GroceryCreate(BaseModel):
    name: str = Field(..., min_length=2, max_length=50)
    category: str
    price: int = Field(..., gt=0)
    quantity: int = Field(..., ge=0)
    expiration_date: date

    @field_validator("name")
    @classmethod
    def sanitize_and_clean_name(cls, value: str) -> str:
        cleaned_text = value.strip()
        if len(cleaned_text) < 2:
            raise ValueError("공백을 제외하고 최소 2글자 이상 입력해야 합니다.")
        return cleaned_text

    @model_validator(mode="after")
    def enforce_expiry_date_safety_policy(self) -> Self:
        if self.expiration_date < date.today():
            raise ValueError("이미 유통기한이 지난 상품은 등록할 수 없습니다.")
        return self
```

이 예시는 Python 3.11 이상에서 제공하는 `typing.Self`를 사용했습니다. 교안의 `typing_extensions.Self`와 목적은 같습니다.

`field_validator("name")`는 이름 항목을 처리합니다. 기본 모드에서는 해당 필드의 타입·길이 검사 후 실행하며, `.strip()`으로 양끝 공백을 제거하고 정리된 이름을 반환합니다. `"  감  "`은 공백 제거 후 `"감"`이 되어 추가 길이 검사에서 실패합니다.

`model_validator(mode="after")`는 필드 검증을 통과한 모델 객체를 받습니다. `self.expiration_date`로 값을 확인하고, 통과하면 `self`를 반환합니다. 날짜 비교가 `< date.today()`이므로 오늘보다 과거인 날짜를 거절합니다. 모델 객체가 만들어졌다는 것은 저장 완료를 뜻하지 않습니다.

이 교안의 등록 흐름은 다음과 같습니다.

```text
요청 JSON
  → 각 필드의 타입·제약 조건 검사 및 필드 검증
  → 모델 after 검증
  → 등록 함수 본문 실행
  → 딕셔너리 변환 및 메모리 장부 저장
  → 응답 모델 검사와 직렬화
  → HTTP 응답
```

등록 모델 검증이 실패하면 저장 함수 본문까지 진행하지 않습니다. 검증기 내부의 `ValueError`는 Pydantic 검증 오류로 처리되며, FastAPI의 요청 본문 검증 과정에서는 기본적으로 422 응답으로 이어집니다.

## 8. 모델 변환, 저장, 응답은 별개

```python
# 등록 함수 본문에서 사용하는 코드 발췌
serialized_data = payload.model_dump()
serialized_data["id"] = grocery_id_counter
grocery_database[grocery_id_counter] = serialized_data
grocery_id_counter += 1
```

`payload`는 개발자가 붙인 변수 이름이며 여기서는 검증된 `GroceryCreate` 객체입니다. `model_dump()`는 데이터를 파이썬 딕셔너리로 꺼냅니다. JSON 문자열 생성이나 저장을 자동으로 수행하지 않습니다. 실제 저장은 `grocery_database[...] = serialized_data`에서 일어납니다.

| 모델 | 사용 시점과 역할 |
|---|---|
| `GroceryCreate` | 함수 실행 전, 사용자가 보낸 등록 데이터 검사 |
| `GroceryResponse` | 함수 반환 후, 응답 데이터의 구조 검사 및 필드 구성 |

서버가 상품 번호를 부여하므로 응답 모델에는 `id`가 포함됩니다. 필수 응답 필드를 빠뜨리는 것은 사용자의 입력 문제가 아니라 서버가 응답을 잘못 만든 문제입니다. 입력 모델의 가격 제한이 응답 모델에 자동으로 복사되는 것도 아닙니다.

## 9. HTTPException과 응답 구성

입력 형식이 올바르더라도 실제 대상이 없을 수 있습니다. 양수인 상품 번호가 검증을 통과했다고 장부에 해당 상품이 있다는 뜻은 아닙니다.

```python
# 단건 조회 함수 본문에서 사용하는 코드 발췌
if item_id not in grocery_database:
    raise HTTPException(
        status_code=404,
        detail="상품이 없습니다.",
        headers={"X-Error-Reason": "ITEM_NOT_FOUND"}
    )
```

`raise`는 현재 정상 실행 흐름을 중단하고 예외를 발생시킵니다. FastAPI가 이를 오류 응답으로 처리하며, 서버 전체를 종료하는 것은 아닙니다.

| 구성 요소 | 예시 | 역할 |
|---|---|---|
| 상태 코드 | `404` | 요청한 대상을 찾지 못함 |
| 본문 | `{"detail": "상품이 없습니다."}` | 구체적인 오류 설명 |
| 헤더 | `X-Error-Reason: ITEM_NOT_FOUND` | 추가 오류 정보 |

`detail`을 바꾸면 본문 메시지가 바뀌고, `headers`를 바꾸면 헤더가 바뀝니다. `X-Error-Reason`은 이 API에서 정한 커스텀 이름이며 오류를 직접 해결하는 기능은 아닙니다.

## 10. 커스텀 예외와 전역 예외 처리기

커스텀 예외는 특정 문제를 표현하기 위해 개발자가 정의한 예외 종류입니다. 교안의 `GroceryExpiredException`은 상품 이름과 유통기한을 담습니다.

```python
from datetime import date
from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse

app = FastAPI()

class GroceryExpiredException(Exception):
    def __init__(self, name: str, expiration_date: date):
        self.name = name
        self.expiration_date = expiration_date

@app.exception_handler(GroceryExpiredException)
async def handle_expired(request: Request, exc: GroceryExpiredException):
    return JSONResponse(
        status_code=400,
        content={
            "success": False,
            "error_code": "GROCERY_EXPIRED",
            "message": f"{exc.name}의 유통기한이 지났습니다.",
            "expired_at": exc.expiration_date.isoformat()
        }
    )
```

위 코드는 예외와 처리기의 연결을 보여주는 독립 발췌 예시입니다. `request`에는 요청 정보가, `exc`에는 발생한 예외 객체가 들어옵니다. `JSONResponse`는 지정한 상태 코드와 JSON 본문으로 응답을 만듭니다.

요청 처리 중 해당 예외가 처리기까지 전달되면 **예외 발생 → 등록된 처리기 실행 → 400 응답**으로 이어집니다. 같은 종류의 예외 응답을 바꾸려면 처리기 한곳에서 수정할 수 있습니다. 모든 프로그램 오류를 무조건 잡는다는 뜻은 아닙니다.

특히 같은 유통기한 문제라도 아래 두 경로를 구분해야 합니다.

| 상황 | 발생 위치 및 예외 | 교안 기준 응답 |
|---|---|---|
| 만료 상품 새 등록 | 모델 검증기에서 `ValueError` | 요청 입력 검증 실패, 422 |
| 저장된 상품 안전 검사 | 검사 함수에서 `GroceryExpiredException` | 전역 처리기의 400 |
| 존재하지 않는 상품 | 조회·검사 함수에서 `HTTPException` | 404 |

처음에는 만료 상품 등록도 커스텀 처리기로 간다고 생각했지만, **문제의 설명이 아니라 실제 발생한 예외 종류와 처리 위치**를 봐야 한다는 점을 정리했습니다. 교안의 일반 단건 조회에는 유통기한 검사가 없으므로 조회만으로 만료 예외가 발생하지 않습니다.

## 11. 실행 명령과 curl — 설명까지 진행, 실제 실행 미확인

교안의 프로젝트 구조는 다음과 같습니다.

```text
grocery-validator/
├── pyproject.toml
├── uv.lock
└── src/
    ├── main.py
    └── schemas/
        └── grocery.py
```

교안에 제시된 환경 구성 및 실행 명령입니다. 이 TIL에서 설치나 서버 실행을 완료했다는 의미는 아닙니다.

```bash
uv init grocery-validator --python 3.13
cd grocery-validator
uv add fastapi uvicorn pydantic
uv run uvicorn main:app --app-dir src --reload
```

- `uv run`: 프로젝트 환경에서 명령 실행
- `uvicorn`: 요청을 받아 FastAPI 앱에 전달하는 서버 프로그램
- `main:app --app-dir src`: `src/main.py`의 `app` 객체 사용
- `--reload`: 코드 변경 시 서버 앱 재시작, 브라우저 새로고침과 다름

교안의 장부는 메모리 딕셔너리이므로 앱이 재시작되면 추가한 상품은 사라지고 코드에 작성된 초기 데이터로 돌아갑니다.

`curl`은 실행 중인 서버에 요청을 보내는 클라이언트 도구입니다. `-X`는 요청 메서드를 지정하고, `-i`는 본문과 함께 응답 상태 및 헤더를 표시합니다.

```bash
curl -i -X GET "http://127.0.0.1:8000/groceries?limit=-5"
curl -i -X GET "http://127.0.0.1:8000/groceries/100"
curl -i -X POST "http://127.0.0.1:8000/groceries/2/verify-safety"
```

위 요청은 교안 기준으로 각각 범위 검증 오류 422, 없는 상품 404, 만료 상품 안전 검사 400을 확인하기 위한 예시입니다. 마지막 결과는 해당 상품이 존재하고 실행일 기준 유통기한이 지났을 때의 예상입니다. 실제 응답을 수집한 결과가 아닙니다.

원문에 섞인 `@file:` 및 `@url:` 표시는 파이썬이나 curl 문법이 아니므로 예시에서는 제거했습니다. 함수 본문 발췌에는 주변 앱·모델·변수 정의가 필요합니다.
