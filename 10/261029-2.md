
## 1. 관심사 분리 — 파일 개수가 아니라 책임

회원 가입·조회는 `users.py`, 배송 등록·조회는 `deliveries.py`, 앱 생성과 라우터 연결은 `main.py`가 담당하도록 구성합니다.

### Q. 파일을 여러 개로 나누면 관심사 분리가 잘된 것인가요?

아닙니다. 같은 가입 규칙을 `main.py`와 `users.py`에 중복 작성하면 하나의 정책을 바꿀 때 두 곳을 수정해야 합니다. 한쪽만 수정하면 서로 다른 조건으로 검사할 위험도 있습니다.

반대로 회원 기능을 `users.py`에 작성하고 `main.py`에서 연결하는 것은 정상적인 역할 분담입니다. 여러 파일을 수정한다는 사실 자체가 문제는 아닙니다.

실제 서비스에서는 요청 처리를 라우터에, 가입 정책을 서비스 파일에 나눌 수도 있습니다. 중요한 것은 파일 간 연결을 없애는 것이 아니라 책임을 명확히 하고 불필요한 변경 전파를 줄이는 것입니다.

## 2. APIRouter — API 경로를 기능별로 묶기

```python
from fastapi import APIRouter

router = APIRouter(prefix="/users", tags=["Users"])

@router.get("")
async def list_users():
    return {"message": "회원 목록"}

@router.post("")
async def register_user():
    return {"message": "회원 가입 처리 예시"}
```

추가 접두사 없이 앱에 연결했다면 `GET /users`와 `POST /users`가 각각 다른 함수에 연결됩니다. 함수 이름보다 등록된 **HTTP 메서드와 경로**가 요청 연결의 기준입니다.

`prefix`와 `tags`는 유용한 설정이지만 문법적으로 필수 인자는 아닙니다.

### Q. tags는 왜 필요한가요? 실제 역할이 있나요?

태그는 API 문서에서 관련 기능을 묶어 보여 주는 이름표입니다. API가 많아지면 개발자가 회원 기능이나 배송 기능을 쉽게 찾도록 돕습니다.

- `prefix`: 실제 요청 경로에 영향을 줍니다.
- `tags`: Swagger UI와 ReDoc의 분류에 영향을 줍니다.
- 태그는 URL 변경, 권한 검사, 처리 속도 향상을 담당하지 않습니다.

### Q. 두 태그 목록이 합쳐진다는 것은 무슨 뜻인가요?

```python
router = APIRouter(prefix="/orders", tags=["Orders"])
# app은 이미 생성한 FastAPI 객체라고 가정합니다.
app.include_router(router, tags=["Service"])
```

이 라우터의 API에는 `Service`와 `Orders`가 모두 적용됩니다. Swagger UI에서 같은 API가 두 그룹 아래 표시될 수 있지만 API가 두 개 생기거나 두 번 실행되는 것은 아닙니다. 기존 태그를 덮어쓰는 것이 아니라 추가하는 것입니다.

### Q. GET만 등록했는데 POST 요청을 보낼 수 있나요?

보낼 수 있습니다. 클라이언트가 요청하는 것과 서버가 그 요청을 처리하도록 등록한 것은 별개입니다.

`GET /users`만 등록되어 있다는 조건에서:

| 요청 | 결과 |
|---|---|
| `GET /users` | 조회 함수 실행 |
| `POST /users` | 경로는 있지만 메서드가 맞지 않아 405 |
| `POST /members` | 등록된 경로가 없어 404 |

`tags=["Members"]`로 바꿔도 `/members`라는 주소가 생기지 않습니다.

## 3. 파일 위치·별명·URL을 구분하기

### Q. import와 include_router는 각각 왜 필요한가요?

```python
from fastapi import FastAPI
from routers.users import router as user_router

app = FastAPI()
app.include_router(user_router)
```

- `import`: 다른 파일의 객체를 현재 파일에서 사용할 수 있게 가져옵니다.
- `as user_router`: 가져온 객체를 현재 파일에서 부를 별명을 지정합니다.
- `include_router`: 그 객체에 모인 API 경로들을 실제 앱에 등록합니다.

`import`만 있고 `include_router`가 없으면 함수와 라우터는 존재하지만 해당 경로가 앱에 연결되지 않습니다.

### Q. users.py를 members.py로 바꾸면 prefix도 바꿔야 하나요?

아닙니다. 파일 위치와 URL은 독립적입니다.

```python
from routers.members import router as member_router
app.include_router(member_router)
```

`members.py` 안의 설정이 `prefix="/users"`라면 요청 경로는 여전히 `/users`로 시작합니다. 파일을 옮기면 import 위치를, 별명을 바꾸면 그 별명을 사용하는 코드도 수정합니다.

| 구분 | 예시 | 역할 |
|---|---|---|
| 파일 위치 | `routers/shipping.py` | 파이썬이 코드를 찾는 위치 |
| 가져오기 | `from routers.shipping import router` | 그 파일의 객체를 가져오기 |
| 별명 | `delivery_router` | 현재 코드에서 객체를 부를 이름 |
| URL 경로 | `/api/orders/cancel` | 클라이언트가 요청하는 주소 |

### Q. URL에는 어떤 부분이 붙나요?

| 설정 | 값 |
|---|---|
| `include_router`의 prefix | `/api` |
| `APIRouter`의 prefix | `/orders` |
| 데코레이터 | `@router.post("/cancel")` |

최종 요청은 **`POST /api/orders/cancel`**입니다. 파일 이름이나 변수 별명은 붙지 않습니다. 메서드와 경로는 구분해서 적으며 실제 URL 내부에는 공백을 넣지 않습니다.

같은 라우터의 `/recent`와 `/register`는 각각 별개의 함수 경로입니다. 앞서 작성한 함수의 경로가 다음 함수에 누적되는 것은 아닙니다.

## 4. Depends — 필요한 작업을 FastAPI에 맡기기

### Q. 의존성은 왜 필요한가요?

API가 실행되기 전에 필요한 권한 검사, DB 연결 준비, 공통 입력 처리 등을 FastAPI가 수행하도록 등록하기 위해 사용합니다.

일반 함수로도 검사 코드를 재사용할 수 있습니다. `Depends`의 추가적인 역할은 FastAPI가 함수 실행과 필요한 입력 연결, 반환값 전달을 관리한다는 점입니다.

### Q. 검사 함수는 어디에 등록하나요?

```python
from fastapi import APIRouter, Depends, HTTPException

def check_access():
    # 흐름 설명을 위해 모든 요청을 거부하는 예시입니다.
    raise HTTPException(status_code=403, detail="접근 거부")

router = APIRouter(prefix="/orders")

@router.get("")
async def list_orders():
    return {"message": "공개 조회"}

@router.post("/cancel", dependencies=[Depends(check_access)])
async def cancel_order():
    return {"message": "취소 완료"}
```

`def check_access()`는 함수 정의입니다. `Depends(check_access)`는 그 함수를 요청 처리 시 실행하도록 등록합니다. 함수 본문에서 직접 호출하지 않아도 FastAPI가 실행합니다.

`/cancel`은 경로이고 실제 검사 설정은 `dependencies=[Depends(check_access)]`입니다. 빈 목록 `dependencies=[]`에는 검사가 없습니다.

### Q. “라우터 전체 검사를 제거한다”는 것은 무엇을 지운 것인가요?

```python
# 변경 전: 모든 API에 검사 적용
router = APIRouter(prefix="/orders", dependencies=[Depends(check_access)])

# 변경 후: 라우터 전체 적용 설정을 제거
router = APIRouter(prefix="/orders")
```

검사 함수 자체를 삭제한 것이 아닙니다. 전체 적용 설정을 빼고 취소 데코레이터에만 등록하면 조회는 공개로 유지할 수 있습니다. 조회 API를 반드시 다른 파일이나 라우터로 옮길 필요는 없습니다.

### Q. include_router에 의존성을 추가하면 기존 조회 API도 영향을 받나요?

그 라우터를 이번에 앱에 연결할 때는 영향을 받습니다.

```python
app.include_router(router, dependencies=[Depends(check_access)])
```

`@router.get(...)`에서 사용한 객체와 위 코드에 전달한 `router`가 같은 객체이므로, 이미 정의한 조회도 연결 대상에 포함됩니다. 앱에 등록되는 모든 해당 API에 검사가 적용됩니다. 원본 라우터 객체를 직접 수정한다는 의미는 아닙니다.

| 등록 위치 | 적용 범위 |
|---|---|
| `include_router(..., dependencies=[...])` | 이번에 연결하는 라우터의 모든 API |
| `APIRouter(dependencies=[...])` | 해당 라우터의 모든 API |
| API 데코레이터의 `dependencies=[...]` | 해당 API |

상위와 하위의 서로 다른 의존성은 함께 적용됩니다. 같은 의존성을 여러 곳에 등록했다고 반드시 여러 번 실행되는 것은 아니며, FastAPI는 기본적으로 요청 안에서 의존성 결과를 캐시합니다.

### Q. 검사 결과를 API 안에서 쓰려면 어떻게 하나요?

```python
async def cancel_order(user=Depends(get_current_user)):
    return {"requested_by": user["id"]}
```

`get_current_user`가 정의되어 있다고 가정한 예시입니다. 반환값이 `user`에 전달됩니다. 반면 데코레이터의 `dependencies=[...]`는 실행은 하지만 반환값을 API의 인자로 전달하지 않습니다.

## 5. return과 raise — 가장 중요했던 질문

### Q. “평범한 데이터를 반환한다”는 것은 무슨 뜻인가요?

```python
def check_access():
    return {"error": "접근 거부"}

@router.post("/cancel")
async def cancel_order(result=Depends(check_access)):
    print(result)
    return {"message": "취소 완료"}
```

`router`와 `Depends`가 준비되어 있다고 가정한 예시입니다.

1. FastAPI가 `check_access`를 실행합니다.
2. 검사 함수가 딕셔너리를 정상적으로 반환합니다.
3. 그 딕셔너리가 `result`에 들어갑니다.
4. `print(result)`는 서버 터미널에 값을 출력합니다.
5. API 함수가 `{"message": "취소 완료"}`를 반환합니다.

`error`라는 키나 “접근 거부”라는 문장은 데이터일 뿐입니다. FastAPI가 문장의 의미를 읽고 실행을 중단하지 않습니다.

**검사 함수의 return은 API 함수로 값을 전달하고, API 함수의 return은 HTTP 응답으로 만들 데이터를 FastAPI에 전달합니다.**

### Q. return도 함수를 끝내는데 왜 취소 처리가 계속되나요?

`return`은 **현재 함수만** 정상 종료합니다. 검사 함수가 끝나면 호출한 FastAPI가 반환값을 받아 다음 작업인 API 함수 실행을 이어갑니다. 전체 요청 처리를 강제로 중단하는 명령이 아닙니다.

### Q. 그러면 return "error"는 언제 쓰나요?

결과를 받은 쪽이 직접 검사하고 다음 행동을 결정하도록 설계할 때 쓸 수 있습니다.

```python
def check_quantity(text):
    if not text.isdigit():
        return "error"
    return "ok"

result = check_quantity("세 개")
if result == "error":
    print("숫자로 다시 입력해 주세요.")
else:
    print("주문을 진행합니다.")
```

실행을 나누는 것은 `"error"`라는 문자열 자체가 아니라 아래의 `if`입니다. 결과를 무시하면 주문 처리가 계속될 수 있습니다. 실제 코드에서는 불리언이나 구조화된 결과를 사용하기도 합니다.

### Q. 접근 거부에는 왜 raise HTTPException을 쓰나요?

```python
from fastapi import Header, HTTPException

def check_access(x_delivery_token: str = Header(...)):
    if x_delivery_token != "safe-delivery":
        raise HTTPException(status_code=403, detail="접근 거부")
    return x_delivery_token
```

`HTTPException(...)`은 예외 객체를 만들고, `raise`는 그 예외를 발생시킵니다. 검사에 실패하면 정상 흐름을 중단하므로 배송 API 함수는 실행되지 않습니다. FastAPI가 예외를 처리하여 403과 `{"detail": "접근 거부"}`를 응답합니다. 서버 전체가 종료되는 것은 아닙니다.

- 실패: `raise`로 정상 흐름 중단
- 성공: `return`으로 확인한 결과 전달
- `return {"status_code": 403}`은 딕셔너리일 뿐, 실제 HTTP 상태를 자동으로 403으로 만들지 않음
- `logger.error(...)`도 로그 기록일 뿐, 접근을 자동으로 차단하지 않음

### Q. 헤더 누락과 잘못된 토큰은 어떻게 다른가요?

`Header(...)`의 `...`는 필수값을 뜻합니다. 기본적으로 `x_delivery_token`은 `x-delivery-token` 헤더와 연결됩니다.

| 상황 | 교안에서의 결과 |
|---|---|
| 필수 헤더 누락 | 요청 검증 실패로 422 |
| 토큰 값 불일치 | 검사 함수가 지정한 403 |
| 토큰 일치 | 의존성 검사 통과 |

고정 토큰 비교는 학습용이며 완성된 사용자 인증 시스템은 아닙니다.

## 6. 미들웨어 — 시간 측정만을 뜻하지 않음

### Q. 미들웨어는 시간 기록하는 기능인가요?

시간 기록은 사용 예시 중 하나입니다. 미들웨어는 API 전후의 공통 길목에서 요청과 응답을 처리하는 구조입니다.

```text
요청 → 미들웨어 전처리 → API
응답 ← 미들웨어 후처리 ← API 응답
```

로그 기록, Host 검사, 공통 응답 헤더 추가, CORS 처리 등에 사용합니다. 모든 미들웨어가 전처리와 후처리를 모두 할 필요는 없습니다.

```python
import time

@app.middleware("http")
async def measure_time(request, call_next):
    start = time.perf_counter()
    response = await call_next(request)
    response.headers["X-Process-Time"] = str(time.perf_counter() - start)
    return response
```

`app`이 준비되어 있다고 가정한 예시입니다. `request`는 들어온 요청이고 `response`는 돌려보낼 응답입니다. `call_next`는 다음 단계로 넘기고, `await`는 응답을 기다리면서 다른 비동기 작업이 진행될 수 있게 합니다. 별도 스레드를 생성한다는 뜻은 아닙니다.

시간 간격 측정에는 시스템 시각 조정에 영향을 받지 않는 `perf_counter()`가 적합합니다. 이 코드는 스트리밍 본문의 전송 완료까지 측정하지는 않습니다.

### Q. 미들웨어 등록 순서는 왜 중요한가요?

직접 추가한 미들웨어 중 시간 측정 A를 먼저, Host 검사 B를 나중에 등록하면 B가 바깥을 감쌉니다.

- 요청: B → A → API
- 응답: API → A → B

B가 Host를 거부하면 A에 도달하지 않으므로 시간 헤더가 없습니다. 반면 의존성의 `HTTPException`이 FastAPI에서 403 응답으로 처리되어 돌아오면 A가 후처리할 수 있습니다. 처리되지 않은 서버 예외까지 언제나 동일하다고 일반화하면 안 됩니다.

사용자 미들웨어에서 직접 차단할 때는 일반적으로 `HTTPException`을 발생시키기보다 `JSONResponse` 같은 오류 응답 객체를 반환합니다.

## 7. TrustedHost와 CORS

### Q. TrustedHost는 누구를 검사하나요?

요청의 `Host`에 적힌 서버 이름이 허용 목록에 있는지 검사합니다. 방문자의 IP나 로그인 권한을 검사하지 않습니다. `localhost`를 허용했다고 로컬 사용자만 인증해 주는 것은 아닙니다.

### Q. CORS는 무엇인가요?

출처는 **프로토콜 + 호스트 + 포트**입니다.

- 프론트엔드: `http://localhost:3000`
- API 서버: `http://localhost:8000`

포트가 다르므로 다른 출처입니다. 브라우저는 기본적으로 프론트 JavaScript가 다른 출처의 응답을 마음대로 읽지 못하게 합니다. CORS는 서버가 허용 정보를 응답 헤더로 제공하고 브라우저가 이를 판단하도록 하는 체계입니다.

```python
from fastapi.middleware.cors import CORSMiddleware

app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://localhost:3000"],
    allow_methods=["GET", "POST"],
    allow_headers=["Content-Type", "X-Delivery-Token"],
)
```

일부 요청은 먼저 OPTIONS 사전 요청으로 메서드와 헤더의 허용 여부를 확인합니다. 실제 요청에 맞춰 출처·메서드·헤더를 설정해야 합니다.

CORS는 인증이 아닙니다. curl은 브라우저의 CORS 제한을 받지 않으며, 일부 요청은 응답 읽기가 막혀도 서버에 도착할 수 있습니다. 따라서 CORS만으로 무단 접근이나 상태 변경을 막는다고 생각하면 안 됩니다.

## 8. 스키마와 JSON 본문

### Q. 스키마는 무엇인가요?

데이터가 어떤 항목으로 구성되고 어떤 조건을 만족해야 하는지 정의한 규칙입니다.

```python
from pydantic import BaseModel, Field

class DeliveryCreateSchema(BaseModel):
    recipient_name: str = Field(..., min_length=2, max_length=50)
    address: str = Field(..., min_length=5)
```

`BaseModel`은 Pydantic의 검증 기능을 사용하게 합니다. `str`은 문자열 필드, `...`는 필수값, 길이 설정은 입력 조건입니다. 타입에 따라 값 변환이 일어날 수 있으므로 모든 입력을 무조건 엄격하게 원래 타입만 받는다고 일반화하지 않습니다.

### Q. JSON 본문은 무엇인가요?

요청에 담아 보내는 실제 데이터를 JSON 형식으로 작성한 부분입니다.

| 요청 구성 | 예시 |
|---|---|
| 메서드·경로 | `POST /deliveries` |
| 헤더 | `Content-Type: application/json` |
| 본문 | 수령인과 주소를 담은 아래 JSON |

```json
{
  "recipient_name": "김민수",
  "address": "서울시 강남구"
}
```

JSON은 데이터 교환용 텍스트 형식이며, 파이썬 딕셔너리 자체는 아닙니다.

```python
@router.post("")
async def create_delivery(payload: DeliveryCreateSchema):
    return {"recipient": payload.recipient_name}
```

흐름은 **JSON 본문 → 스키마 검증 → payload 객체 → API 함수**입니다. 이름이 한 글자이거나 주소가 빠지면 검증에 실패하고 API 함수는 실행되지 않습니다.

**JSON은 제출한 실제 데이터, 스키마는 그 데이터가 지켜야 할 규칙**입니다. 스키마는 저장소가 아니며, 길이 검증만으로 실제 존재하는 주소인지 알 수 없습니다.

### 요청 스키마와 응답 스키마

- 요청 스키마: 클라이언트가 보낸 데이터 검증
- `response_model`: 서버 반환 데이터 검증과 필터링
- `status_code=201`: 정상 생성 응답의 상태 지정
- `delivery_status: str = "WAITING"`: 기본값이며 허용값을 WAITING 하나로 제한하지 않음
- `email: str`: 문자열 규칙일 뿐 이메일 형식 검사까지 하지 않음

응답 모델에 맞지 않는 서버 반환값은 서버 쪽 오류이며, 클라이언트 입력 오류 422와 구분합니다.

## 9. 인메모리 저장·로깅·실행 명령

### 인메모리 저장

`user_db`와 `delivery_db`는 파이썬 리스트입니다. 프로세스 재시작 시 데이터가 사라지고, 여러 워커 간에 자동 공유되지 않습니다. 영구 DB를 대신하는 학습용 구조입니다.

`global delivery_sequence`는 함수 밖의 변수에 새 값을 대입할 때 필요합니다. 리스트 객체에 `append`만 하는 것은 변수 자체의 재대입과 다릅니다.

### 로깅 모듈화

메인에서 `logging.basicConfig(...)`로 공통 설정을 하고 각 파일에서 `logging.getLogger("delivery_system.users")` 같은 이름 있는 로거를 사용합니다. 기본 전파 설정에서 상위 로거의 핸들러를 통해 일관된 형식으로 출력할 수 있습니다.

- INFO: 정상 동작 정보
- WARNING: 주의가 필요한 상황
- ERROR: 오류 상황

로그 수준 자체는 예외 발생이나 요청 차단 명령이 아닙니다. `basicConfig`는 루트에 이미 핸들러가 있으면 보통 아무 작업도 하지 않습니다.

### 실행 환경

```bash
uv init order-delivery-system --python 3.13
cd order-delivery-system
uv add fastapi uvicorn pydantic
uv run uvicorn main:app --app-dir src --reload
```

- `uv`: 프로젝트·의존성·실행 환경 관리
- `Uvicorn`: FastAPI 앱을 실행하는 ASGI 서버
- `main:app`: main 모듈의 app 객체
- `--app-dir src`: 모듈 검색에 src 사용
- `--reload`: 코드 변경 시 개발 서버 재시작

교안의 폴더 설명 중 `digital-menu`는 실제 명령의 `order-delivery-system`과 불일치합니다. curl 예시의 `@url:` 표시도 실제 URL 문법이 아니므로 제거해야 합니다.

## 10. 전체 연결 정리

```text
앱 준비
파일에서 router 가져오기
→ include_router로 API 등록
→ 미들웨어 설정과 함께 앱 실행

요청 처리의 개념적 흐름
클라이언트 요청
→ 바깥 미들웨어 검사
→ 안쪽 미들웨어 전처리
→ 경로 매칭·입력 검증·의존성 처리
→ API 업무 처리
→ 응답 모델 처리
→ 미들웨어 후처리
→ 클라이언트 응답
```

입력 검증과 의존성 처리를 모든 경우에 하나의 고정된 세부 순서로 단순화하지는 않습니다. 핵심은 필요한 검증과 의존성이 정상적으로 해결되어야 API 본문이 실행된다는 점입니다.

오늘의 핵심 구분은 다음과 같습니다.

- **라우터:** 기능별 API를 묶음
- **include_router:** API를 실제 앱에 연결
- **Depends:** 필요한 검사·준비 작업 실행과 결과 전달
- **raise:** 정상 흐름을 중단하고 예외 처리로 전환
- **미들웨어:** 요청·응답의 공통 길목 처리
- **스키마:** 데이터 구조와 검증 규칙
- **JSON 본문:** 클라이언트가 실제로 제출한 데이터
