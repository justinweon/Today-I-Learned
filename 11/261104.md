# OAuth2 인증 표준과 JWT 블랙리스트 보안

### Authentication VS Authorization(인증 VS 인가)

| **구분** | **인증 (Authentication)** | **인가 (Authorization)** |
| --- | --- | --- |
| **핵심 질문** | "당신은 누구인가요?" (신원 확인) | "당신은 이 방에 들어올 수 있나요?" (권한 허가) |
| **대표 예시** | 아이디/비밀번호 입력, 지문 인식 | 일반 회원의 관리자 페이지 접근 제한, 글 수정 권한 확인 |
| **실행 시점** | 서비스 접속 시 최초 1회 수행 | 인증을 마친 사용자가 특정 정보나 기능을 요청할 때마다 수행 |

- 토큰 기반의 인증 방식... 토큰?

## 토큰
토큰은 상품권에 비유. 어떤것을 교환할 수 있는 토큰. 재화/서비스 등. 영화티켓, 백화점 상품권 같은것! <br> 하지만 컴퓨터세계에서는 <b>정보</b>를 교환하는 교환권. 

이런 교환권, 토큰은 실제로 믿을 수 있는 출처에서 왔는지 검증을 하고, 검증이 되면 서비스를 제공. 

클라이언트가 토큰을 헤더에 실어서 서버에 보냄. 토큰을 실어보내면 이 토큰을 무작정 믿지 말고 검증을 해야한다는 것. 서버와 클라이언트가 서로 믿을 수 없기 대문에 <i>인증 서버로 부터 맞는지 검증을 해야함.</i>


서버에서, 인증서버로 토큰을 보내고, 검증이 되면 서비스를 제공한다. <b>토큰 인증 방식</b>

oAuth 인증 방식은 이 토큰 방식. 

## JWT

JWT (JSON WEB TOKEN) 표준 토큰은 기본 정보를 토큰에 포함하고 있음. 식별ID나 만료시간 발행시간 등등... 그래서 DB에 기록할 필요가 없다. 토큰의 길이가 김. 개인정보를 담고 있는 형태이기 때문.

개인정보가 담겨있다? 보안문제가 발생할 수 있다. 아주 큰 문제. payload쪽만 풀면 다 알 수 있다. 

구조는 `Header.Payload.Signature` 세 부분을 .으로 이은 형태. payload부분이 토큰에 포함된 데이터. JWT표준 형식이 있어서 JSON문자열로 구성하고 
- sub에는 식별자ID(회원 ID)
- hti는 토큰 식별자 ID
- exp는 토큰 만료시간
- iat (issued at) 은 토큰 발급일시

헤더쪽에는 두가지가 정의 되는데, 알고리즘 유형(alg, 암호화 방식)과 토큰유형 (JWT) 

검증에 대한 암호화 방식. 서버쪽에는 비밀키와 데이터를 바탕으로 시그니처를 만듬. 데이터가 바뀌면 시그니처가 바뀌기 때문에 변조를 감지할 수 있음. 

시그니처 -> 데이터 변조 검증용 시그니처 문자열. 서버비밀키와 메세지(데이터) 를 바탕으로 시그니처를 만듬. HASH 메세지가 포함된 해시, HMAC이라고 함. 

바뀐 시그니처를 바탕으로 데이터가 바뀌었군! 안돼! 라고 막음.

## 비밀번호 암호화와 Bcrypt원리

비번을 탈취당해도 사용하지 못하는 형태로 저장해서 사용. 보통 비번은 암호화 되어있음. 

비번은 사용자가 입력하면 평문값, 해시는 그 비번을 해시 함수에 넣어 나온 결과값. 이렇게 해시화를 해야 db가 털려도 비번을 바로 알 수 없음. 

#### 암호화
 - 양방향성 (암호화 <-> 복호화)
 - 단방향성 (암호화는 되지만 복호화는 안됨. 해시값에서 원래 비번을 되돌릴수 없다는 뜻) = HASH. 같은 값에서 같은 해시가 나온다. 
 
 요즘은 무차별로 대입 공격을 하기 때문에 고정해시는 쓰면 안됨. 로그인을 위한 비번으로는 쓰지 않고, 요즘은 데이터 변조를 확인할떄 단방향 고정해시를 많이 씀. 인증에서는 사용 X

 그래서 유동해시(adaptive hash)를 쓰게됨 -> Bcrypt. Bcrypt는 생성할떄마다 새로운 해시값이 나옴. 

#### Bcrypt
 bcrypt의 해결책은... 일부러 느리게 만드는 것. 느린 정도를 다이얼로 조절. 
 ```
 cost = 10  → 계산 1024번 반복 (약 0.1초)
cost = 11  → 2048번 반복 (약 0.2초)  ← 숫자 1 올리면 2배 느려짐
cost = 12  → 4096번 반복 (약 0.4초)
```
이런식으로 느리게 만들면 사용자 입장에서는 0.1초 느려져도 상관없지만, 해커입장에서는 후보를 수십억번 시도해야해서 해킹이 불가능해짐. 그래서 "adaptive"라는 말이 붙은 것. 조정가능.

Bcrypt는 해쉬화, 해쉬 검증 두가지. 유동 해쉬이기 때문. 

salt 비번 앞이나 뒤에 붙는 무작위 문자열. 소금치듯 비번에 섞는다는 뜻. 
```
$2b$10$N9qo8uLOickgx2ZMRZoMye IjZAgcfl7p92ldGxad68LJZdL17lhWy
 버전  cost   └──── 솔트 ────┘ └──────────── 해시 ────────────┘
```


## 인증 과정

요청 헤더에
```Authorization: Bearer ${ACCESS_TOKEN}``` 을 심어서 발송. '토큰을 품고있다'

두 가지 방식이있는데;

| | Basic | Bearer |
|---|---|---|
| 보내는 값 | `username:password`를 Base64 인코딩한 것 | 액세스 토큰 |
| 헤더 예시 | `Authorization: Basic dXNlcjpwYXNz` | `Authorization: Bearer eyJhbGciOi...` |
| 자격 증명 성격 | 계정 비밀번호(영구적) | 임시 토큰(만료, 권한 범위 제한) |
| 용도 | 클라이언트 인증, 단순 API | 인가된 API 호출 |

## SOLID 원칙 

객체지향 설계에서 유지보수하기 쉽고 변경에 강한 코드를 만들기 위한 5가지 원칙. 앞글자를 딴 말임.

### S: 단일 책임 원칙 (SRP, Single Responsibility)
- 클래스는 하나의 책임(변경 이유)만 가져야 함.
- 이메일 정책이 바뀌어도 `UserService`는 수정할 필요가 없도록 역할별로 분리함.

```java
// 나쁜 예: 회원 저장 + 이메일 발송 + 로그 기록을 한 클래스가 다 함
class UserService { save(); sendEmail(); writeLog(); }

// 좋은 예: 역할별로 분리
class UserService { save(); }
class EmailSender { send(); }
class Logger { write(); }
```

### O: 개방-폐쇄 원칙 (OCP, Open-Closed)
- 확장에는 열려 있고, 수정에는 닫혀 있어야 함.
- 새 기능을 추가할 때 기존 코드를 고치지 않고 새 코드를 덧붙이는 방식이어야 함.
- `if (type == "A") ... else if (type == "B")`가 계속 늘어나면 OCP 위반 신호임.

```java
interface Discount { int apply(int price); }
class RateDiscount implements Discount { ... }
class FixedDiscount implements Discount { ... }  // 추가해도 기존 코드 수정 없음
```

### L: 리스코프 치환 원칙 (LSP, Liskov Substitution)
- 자식 클래스는 부모 클래스를 대체해도 문제없이 동작해야 함.
- 대표적인 위반 사례는 `Bird`를 상속한 `Penguin`임. `Bird.fly()`를 호출했는데 펭귄이 예외를 던지면 부모 자리에 자식을 넣을 수 없음.
- 이럴 땐 상속 구조 자체를 다시 설계함. (예: `FlyingBird`와 `Bird`로 분리)

### I: 인터페이스 분리 원칙 (ISP, Interface Segregation)
- 클라이언트가 쓰지 않는 메서드에 의존하면 안 됨.
- 인터페이스는 작고 구체적으로 나눔.

```java
// 나쁜 예
interface Worker { work(); eat(); }
class Robot implements Worker { eat() { /* 필요 없는데 구현 강제 */ } }

// 좋은 예
interface Workable { work(); }
interface Eatable { eat(); }
```

### D: 의존관계 역전 원칙 (DIP, Dependency Inversion)
- 구체 클래스가 아니라 추상화(인터페이스)에 의존해야 함.
- 구현체는 외부에서 주입(DI)함. DB를 MySQL에서 MongoDB로 바꿔도 `OrderService`는 그대로임.
- 테스트할 때 가짜(Mock) 객체를 끼워 넣기도 쉬움. Spring의 DI가 이 원칙을 활용함.

```java
// 나쁜 예: MySQL에 직접 의존
class OrderService { private MySqlRepository repo = new MySqlRepository(); }

// 좋은 예: 인터페이스에 의존하고 구현체는 외부에서 주입
class OrderService {
    private OrderRepository repo;
    OrderService(OrderRepository repo) { this.repo = repo; }
}
```

#### 정리

| 원칙 | 핵심 한 줄 | 위반 신호 |
|---|---|---|
| SRP | 하나의 클래스, 하나의 책임 | 클래스가 너무 크고 수정 이유가 여러 개임 |
| OCP | 기능 추가 시 기존 코드 수정 금지 | `if-else`, `switch`가 계속 늘어남 |
| LSP | 자식은 부모를 대체 가능해야 함 | 자식에서 예외를 던지거나 동작을 무력화함 |
| ISP | 인터페이스는 작게 분리 | 쓰지 않는 메서드를 구현해야 함 |
| DIP | 추상화에 의존 | 코드 안에서 `new 구체클래스()`를 직접 생성함 |

- SOLID는 절대적인 규칙이 아니라 지침임. 작은 프로젝트에서 과하게 적용하면 오히려 코드가 복잡해질 수 있음.
